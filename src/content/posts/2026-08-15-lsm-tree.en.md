B-trees optimize reads; LSM-Trees optimize writes. That single trade-off explains most modern KV stores. Instead of writing in place, an LSM-Tree appends everything to an in-memory table and periodically flushes it to disk as immutable files.

## The write path

A write hits the WAL first, then the memtable. When the memtable fills up, it freezes into an SSTable — a sorted string table — and a fresh memtable takes over. Reads check the memtable, then SSTables from newest to oldest, with a Bloom filter per file skipping the ones that cannot possibly contain your key.

```go
func (db *DB) Put(key, value []byte) error {
    if err := db.wal.Append(key, value); err != nil {
        return err
    }
    return db.memtable.Set(key, value)
}
```

## Compaction: paying debt down

- Size-tiered: merge similarly-sized tables — great write bursts, worse space amplification
- Leveled: each level is 10x the previous, overlapping runs merged downward — predictable reads, more write amplification
- GojiDB uses leveled compaction with per-level Bloom filters to keep read amplification bounded

> Every storage engine is a bet on which cost your workload can afford: write amplification, read amplification, or space.
